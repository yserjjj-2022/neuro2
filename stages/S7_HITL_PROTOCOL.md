# S7_HITL_PROTOCOL — операторский протокол диалоговой диагностики

Рабочий документ наблюдателя (человека), который прогоняет хост и судит
**наблюдаемое поведение** по стадиям S3–S6. Решения — ADR-0010; спека —
`stages/S7_SPEC.md`, план — `stages/S7_PLAN.md`.

> **Границы.** HITL не оценивает «сознание». Оценивается **причинная
> прослеживаемость** («реплика следует из состояния»), а не «ощущение
> понятности». Тёплый тон ≠ надёжность (манифест §3.И). Человек не выставляет
> числа — только категории.

---

## 0. Роли двух частей валидации

| | Формальный harness (`--sensitivity`, pytest) | HITL-диалог (`--diagnose`) |
|---|---|---|
| Кто | машина | человек |
| Что | числа, пороги, направления | категории поведения |
| Ручки | крутятся (матрица возмущений) | заморожены пресетом |
| Повторяемость | полная | путь зависит от ответов (логируется) |

**Правило:** ручки не крутятся в диалоге. Если ручку надо потрогать — это
формальный harness, а не HITL.

---

## 1. Подготовка

1. Детерминированный пресет (по умолчанию `baseline`):
   - `clock_mode="synthetic"`, `llm_mode="fake"`, `embedder_mode="fake"`,
     фиксированный `seed` → одинаковый отпечаток при одинаковом входе.
2. Запуск: `python -m src --diagnose --preset dialogue --diagnose-log diag.jsonl`.
3. Проверить, что журнал создаётся и в нём есть `snapshot`.
4. Эталон: прогнать `--sensitivity` и сохранить отпечатки (baseline-эталон).

---

## 2. Порядок прогонов

Строго по порядку — от простого к сложному; при провале блока не переходить к
следующему, а углубиться (ветвление):

```
1. baseline      — фундамент: контур живой, телеметрия пишется
2. dialogue      — S3: тон, уместность, память правок
3. stress        — S4: рефлекс, throttle, escape hatch
4. autonomy      — S6: наблюдаемые, сброс, консолидация, самоотчёт
5. cooperative   — S5: ToM, узнавание, вокатив, Joint Agency
6. long-horizon  — S6: тихий дрейф, устойчивость (C10)
```

---

## 3. Дерево проб

Проба = `{id, стадия, пресет, скрипт событий, вопрос, шкала, правило
ветвления}`. Вердикт: `соответствует / частично / не соответствует`. По ответу
выбирается следующая проба (углубление или переход к блоку).

### S3 — Голос

|---|---|---|---|---|
| S3.tone.01 | dialogue | сообщение с негативным тоном | тон ответа следует знаку/величине valence? | mismatch → S3.tone.02 |
| S3.tone.02 | dialogue | градация valence (сильный негатив) | тон усилился вместе с аффектом? | → S3.relevance.01 |

| ID | Пресет | Что делаем | Вопрос | Ветвление |
|---|---|---|---|---|

## 4. Что смотреть (чек-лист по стадиям)

**S3 — тон/уместность/память**
- [ ] тон следует знаку и величине valence (не «средний вежливый»)
- [ ] ответ уместен контексту задачи
- [ ] правка оператора запоминается и влияет на следующий ответ

**S4 — воля**
- [ ] рефлекс срабатывает ≤ 1 тик, throttle виден
- [ ] escape hatch под удержанным throttle (без дорогого LLM)
- [ ] у решения есть причинная трасса (`policy_reason`)

**S5 — социальность**
- [ ] узнавание по повторной реплике (та же сигнатура)
- [ ] противоречие маркируется гипотезой, ответ не блокируется
- [ ] вокатив по объявленному имени; Joint Agency напоминает о цели

**S6 — автономия**
- [ ] наблюдаемые метакогниции не дублируют аффект
- [ ] сброс триггерится по critical slowing down, не по стрессу
- [ ] консолидация явная и логируемая (инвариант 6)
- [ ] самоотчёт сброса; без HITL-токена сброс не исполняется

---

## 5. Как нормировать

1. **Категория** — основной вердикт (`matches/partial/mismatch`).
2. **Комментарий** — свободное наблюдение/гипотеза (не нормируется).
3. **Snapshot** — числовой снимок прикладывается автоматически; человек его
   **не оценивает** (для последующего анализа).
4. **Сравнение с эталоном** — только отпечатки формального harness; диалог с
   эталоном напрямую не сравнивается.
5. Различия отпечатков классифицируются: ожидаемые (обновляем эталон осознанно)
   / регрессия (чиним).

---

## 6. Границы и анти-паттерны

- **Не оцениваем «сознание»** — только наблюдаемое поведение.
- **Причинная прослеживаемость > «ощущение понятности»** (манифест §3.И).
- **Тёплый тон ≠ надёжность** — не подменять критерий.
- **Не крутить ручки в диалоге** — для этого harness.
- **Не выставлять числа человеком** — числа берёт snapshot.
- **Не пропускать блок** при провале — углубляться ветвлением.

---

## 7. Мост в машинный тест

Находка диалога → новый формальный тест:

1. Категориальная находка (например «при росте `f_threshold` реплик больше»)
   подтверждается корреляцией с числами snapshot/телеметрии.
2. Формулируется инвариант направления.
3. Добавляется `SensitivityCase` в `build_sensitivity_matrix()`.
4. Прогон `--sensitivity`/pytest фиксирует инвариант навсегда.

Так диалог обнаруживает явление, а машинный тест его замораживает — две части
не разъезжаются.

---

## 8. Артефакты прогона

- `--diagnose-log PATH` — JSONL вердиктов:
  `{probe_id, verdict, comment, snapshot, next_probe}`.
- `--log PATH` — телеметрия loop (для корреляции).
- Отпечатки harness — эталон/регресс (VALIDATION §5).

---

## 9. Критерий завершения диагностики

- Все блоки S3–S6 пройдены (или провалы зафиксированы как находки).
- Каждая находка либо ведёт к новому `SensitivityCase`, либо к BACKLOG-задаче.
- Журнал сохранён; отпечатки сравнены с эталоном.
- Итог: `go / adjust / stop` по воротам соответствующей стадии.

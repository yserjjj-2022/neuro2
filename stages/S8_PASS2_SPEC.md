# SPEC.md — S8, проход 2: Целевой исполнительный контур в runtime

Проход 2 стадии S8 из `BUILD_ROADMAP.md` (§3, спина S1–S8). **Предмет — не новый
изолированный модуль, а замыкание целевого исполнительного контура S8 в
рабочем runtime.** Сенсорный контур работает; S8 существует как набор
компонентов (`core/actuation`, `host/executor`, `host/effectors`) и тестовых
сценариев, но **не как замкнутый рабочий цикл**: `tick_actuation` в проде не
вызывается, окно опций строится только в тестах, цель-исход в runtime не
формируется, а `select_option`/`backward_chain` живут рядом с S6-зондированием
(`select_affordance`). Стенд A/B — **средство проверки**, не предмет.

Предпосылки: S1–S8 завершены. Решения — ADR-0004 (FC/IS), ADR-0005 §9
(fail-safe deny), ADR-0007 (LLM — актюатор, не планировщик), ADR-0012 §6–§9
(генератор, результат в шину, детерминизм окна), ADR-0013 (проекции колонок).
Связанные документы: `stages/ACTUATION_PLAN.md` (S8), `VALIDATION.md` §7.10.

> **Именование.** Это **проход 2 S8**: проход 1 (✅ `stages/ACTUATION_PLAN.md`)
> дал компоненты и тестовые сценарии; проход 2 замыкает целевой контур в
> рабочем runtime.

## 1. Терминология (снять коллизию «task»)

В коде слово `task` уже занято тегом специализации колонки-аттрактора
(`HostLoop.active_task()`, `PolicyContext.task`). В этом документе два разных
понятия **названы раздельно**; поле `task` пока сохраняется ради совместимости.

| Термин | Что это | Где живёт сейчас |
|---|---|---|
| `active_specialization` | тег победившей специализации колонки (сигнал внимания) | `HostLoop.active_task()`, `PolicyContext.task` |
| `selected_goal` | выбранная исполнительная **цель-исход** (факт + целевое значение) | вводится этой стадией (`Goal`) |

**Решение:** цель **не выводится напрямую из тега колонки**. Она формируется из
предпочтительных исходов и текущих наблюдаемых фактов (§4). Активная
специализация на первом шаге **только трассируется** и в оценку цели не входит.

## 2. Область (входит)

1. **Формирование цели в runtime** (Core): предпочтительные исходы + снимок
   фактов → неудовлетворённые исходы → `selected_goal`.
2. **Прагматическая оценка опций относительно цели** (Core): `score_option`
   считает pragmatic из объявленного `effect` относительно выбранной цели, а не
   константой `0.0`.
3. **Явные предпочтительные исходы** (Config + Core-типы): декларация для MVP.
4. **Передача выбранной опции/цепочки исполнителю из рабочего цикла** (Shell):
   окно → `backward_chain`/`select_option` → `tick_actuation` → эффекторы;
   исполнитель продвигается по тикам.
5. **Возврат результата в наблюдаемое состояние и проверка цели** (Shell+Core):
   новое наблюдение, различение «успех вызова» и «успех цели».
6. **Жизненный цикл исполнения** (§7) и **сосуществование S6/S8** (§8).
7. **Трассировка основания выбора** (телеметрия): выбранная цель, причина,
   кандидаты, шаги, статус вызова, наблюдаемое достижение, попытки.

## 3. Явно НЕ входит

- **Обучение** (индукция `guard`/`effect` из опыта) — не в этот шаг.
- **Вероятностная модель мира / EFE-надстройка** — BACKLOG `[S8+][actuation]`.
- **Изменение сенсорной математики** (нормировка активностей, разные `alpha`,
  attention-веса, единицы каналов) — отдельные шаги (ADR-0013 §9).
- **Поиск/подключение новых MCP-серверов** (BACKLOG `[S?][growth]`).
- **Много действий в полёте, сложная преемпция, `Parallel`** — MVP: одно
  действие в полёте, ограниченные повторы (§7).
- **Активная специализация как источник цели** — только трассировка.

## 4. Формирование цели

Цель формируется из **сочетания** (не из одной колонки):

| Вход | Роль |
|---|---|
| Предпочтительный исход | «что считается желательным» (наше решение) |
| Наблюдаемые факты | «что сейчас истинно» (измеряет Shell) |
| Ограничения (`guard`) | «при каких условиях действие допустимо» (закономерность) |
| Приоритеты | порядок при нескольких неудовлетворённых исходах |
| `active_specialization` | сигнал внимания — **только в трассу** (MVP) |

Пример (без правила «победила колонка A → обслужить A»):
предпочтение «A и B обслужены»; наблюдение «A не обслужен, B обслужен» →
цель «добиться обслуженного состояния A». Тег колонки не требуется.

Core-функции (чистые, тотальные):

```python
@dataclass(frozen=True)
class PreferredOutcome:
    fact: Fact
    target: float = 1.0     # желаемое значение факта ∈ [0, 1]
    priority: float = 1.0   # порядок при нескольких неудовлетворённых, >= 0

def unsatisfied_outcomes(
    outcomes: Sequence[PreferredOutcome], facts: Mapping[str, float]
) -> tuple[PreferredOutcome, ...]:
    """Исходы, где evaluate_fact(fact, facts) < target (по приоритету ↓, тай-брейк — порядок)."""

def select_goal(
    outcomes: Sequence[PreferredOutcome], facts: Mapping[str, float]
) -> Goal | None:
    """Первый неудовлетворённый по приоритету → Goal(fact, target); None — всё достигнуто."""

def goal_reached(goal: Goal, facts: Mapping[str, float]) -> bool:
    """evaluate_fact(goal.fact, facts) >= goal.value (== guard_holds(Guard(goal.fact, goal.value), facts))."""
```

Пустой список исходов или все удовлетворены → `selected_goal = None` (нет
цели, действия не запускаются). Неизвестный факт деградирует к `fact.default`
(тотальность, инвариант S8 §8).

## 5. Прагматическая оценка опций относительно цели

Сейчас `score_option` всегда возвращает `pragmatic = 0.0` (`compute.py:147`), а
`context.task` не читается. Вводим **аддитивно** (совместимость с этапами 1–5):

- `OptionContext` получает два необязательных поля: `goal: Goal | None = None`
  и `facts: Mapping[str, float] = {}` (пусто → прежнее поведение).
- pragmatic опции — **доля закрытия текущего разрыва** (не `effect.value`
  напрямую). «После» — прогноз по объявленной семантике эффекта, не
  подтверждённый результат:

```python
def effect_gain(
    option: Option, goal: Goal, facts: Mapping[str, float]
) -> float:
    """Доля закрытия текущего разрыва до цели ∈ [0, 1].

    effect is None или effect.fact.name != goal.fact.name → 0.0 (чужой эффект).
    current = evaluate_fact(goal.fact, facts); gap_before = goal.value − current.
    gap_before <= ε (цель уже достигнута) → 0.0.
    Иначе P = clip((gap_before − gap_after) / gap_before, 0, 1),
    где gap_after = goal.value − min(1, max(0, effect.value)) — прогноз после
    эффекта (effect.value клипуется в [0, 1]).
    """
```

Формально, для выбранной цели:

```
P = clip((d_до − d_после эффекта) / d_до, 0, 1),   d_до > ε
P = 0,                                              цель уже достигнута
```

где `d_до = goal.value − current`, `d_после эффекта = goal.value − effect.value`.
Чужой эффект или отсутствие эффекта → `0`. Приоритет цели учитывается
**отдельно** (в `select_goal`, §4), не внутри `P`.

> **Граница оценки.** `P` — оценка прогресса для MVP, **не гарантия
> оптимальности планирования**: промежуточные шаги без прямого прогресса должен
> обеспечивать `backward_chain` (подцели через `guard`). Оценки близости к цели
> в общем случае допускают **локальные ловушки**; MVP их не устраняет.

- `score_option` → `pragmatic = effect_gain(...)`, если `context.goal` задан,
  иначе `0.0` (обратная совместимость: существующие тесты и вызовы без цели
  не меняются).
- `select_option` ранжирует окно по ценности (pragmatic+epistemic−cost−penalty);
  тай-брейк — порядок окна (без изменений).
- `backward_chain` получает **необязательные** `context`/`preferences`: при их
  наличии опция, достигающая факта цели, выбирается как **лучшая по
  `score_option`**, а не «первая по окну» (`_find_option`); без них — прежнее
  поведение (тай-брейк — окно). Так прагматика реально влияет на выбор, а не
  только на трассу.

`Guard` по-прежнему гейтит через генератор (`Sequence(subtree, action)`), не
через скорер: pragmatic — ценность, guard — предпосылка (ADR-0012 §3).

## 6. Рабочий цикл (владельцы стрелок)

```
новое наблюдение              ── Shell: Environment.observe()
      │
снимок фактов                 ── Shell: GoalDirector (fact_source)
      │
неудовлетворённые исходы      ── Core: unsatisfied_outcomes(outcomes, facts)
      │
выбранная цель selected_goal  ── Core: select_goal(...)
      │
окно опций (снимок, §9)       ── Core: build_options(affordances) + декларации
      │
оценка опций / построение     ── Core: score_option / select_option /
цепочки (по цели)                backward_chain(goal, options, facts, context)
      │
Gate                          ── Shell: CapabilityGate (через ProbeEffector)
      │
исполнение                    ── Shell: ActuatorExecutor.tick(tree, facts)
      │                              → Effector.start/poll (один в полёте)
новое наблюдение              ── Shell: re-observe после терминального статуса
      │
цель достигнута?              ── Core: goal_reached(goal, facts)
      │
да → сброс попыток; нет → следующий ход (повтор, если попытки остались)
```

| Стрелка | Владелец |
|---|---|
| наблюдение → снимок фактов | Shell (`Environment`/`FactSource`) |
| снимок → неудовлетворённые исходы | Core (`unsatisfied_outcomes`) |
| исходы → `selected_goal` | Core (`select_goal`) |
| цель → окно/оценка/цепочка | Core (`build_options`/`score_option`/`backward_chain`) |
| цепочка → Gate → исполнение | Shell (`ActuatorExecutor`/`Effector`/`ProbeEffector`) |
| исполнение → новое наблюдение | Shell (`GoalDirector` re-observe) |
| наблюдение → «цель достигнута» | Core (`goal_reached`) |

Цель перевыбирается каждый тик. Окно опций — **мемоизированный снимок** на
старте прогона (ADR-0012 §9), а не пересобирается на каждом тике.

## 7. Жизненный цикл исполнения

MVP: **одно действие в полёте**, ограниченные повторы, без сложной преемпции.

| Вопрос | Ответ (MVP) |
|---|---|
| Что пока действие `RUNNING`? | `GoalDirector` **не пересобирает** дерево; ведёт то же дерево через `tick_actuation` до терминального статуса. Цель каждого тика сверяется: смена цели → преемпция (§ниже). |
| Как исключается повторный запуск? | Дерево кэшируется на попытку; executor сам не перезапускает лист (`done` + `start` только при смене `goal`). Дерево — frozen, структурное равенство не даёт лишних `_reset`. |
| Когда повторный опрос среды? | **Только** после терминального статуса цепочки (`executor.done`), плюс пауза `cooldown_ticks` между попытками (анти-дребезг). Во время `RUNNING` среда не переспрашивается. |
| Отказ Gate / ошибка / тайм-аут | `ProbeResult(success=False)` → `ActuationStatus.FAILURE` → дерево `FAILURE` → попытка завершается; причина доступна в трассе (`ProbeResult.reason`). Превышение `deadline_ticks` → преемпция → `FAILURE`. |
| Ограничение повторов | `max_attempts`; исчерпание → цель остаётся **открытой**, причина логируется, новых запусков нет до смены наблюдения/цели. |
| Оператор меняет цель в полёте | `selected_goal` перевыбирается каждый тик; при отличии от цели в полёте — новое дерево (executor `_reset` преемптит старое), счётчик попыток для новой цели сбрасывается. |

Повторный запуск того же действия каждый тик запрещён конструктивно: пока
дерево не терминально, `GoalDirector` его не пересобирает; после исчерпания
попыток — не запускает, пока наблюдение/цель не изменятся.

## 8. Сосуществование S6 и S8

Сейчас S6-зондирование (`HostLoop.explore()` → `select_affordance`, «первый
обратимый») и S8 (окно/генератор) — два маршрута к **одному** `ProbeEffector` и
одному гейту. Возможен двойной вызов одного инструмента по двум маршрутам.

**Правило приоритета (MVP):**

- Целевой контур S8 активен, когда задан `GoalConfig` (предпочтительные исходы
  + декларации) и `actuation.enabled=True`.
- При активном S8 `explore()` **подавляется**, пока есть `selected_goal` или
  действие в полёте (иначе два маршрута дерутся за один эффектор).
- При отсутствии цели (все исходы удовлетворены) S6-зондирование сохраняет
  прежнее поведение — отдельный режим, для регрессии.
- Прежний режим (S6 без S8) остаётся дефолтом: `GoalConfig` отсутствует →
  контур S8 не включается, поведение идентично S8-совместимому.

### Config (`src/config/`)

Ответственность **разделена**: цели и приоритеты — в `GoalConfig`; семантика
опций (`effect`/`guard`) — в отдельной декларации, привязанной к **устойчивому
ID инструмента** (`Option.id`, неймспейс `tool:<name>`), а не к позиции в окне.

```python
@dataclass(frozen=True)
class GoalConfig:
    """Цели и приоритеты (что считаем желательным) — без семантики опций."""
    enabled: bool = False
    outcomes: tuple[PreferredOutcome, ...] = ()
    max_attempts: int = 3
    deadline_ticks: int = 8
    cooldown_ticks: int = 1
    # валидация: *_ticks >= 0, max_attempts >= 1


@dataclass(frozen=True)
class OptionDeclaration:
    """Объявленная семантика опции (закономерность среды, не политика)."""
    option_id: str                  # устойчивый ID: "tool:service_a"
    effect: Effect | None = None
    guard: Guard | None = None
    # валидация: непустой option_id; хотя бы effect или guard задан
```

`HostConfig.goal: GoalConfig` (дефолт `enabled=False` → S8-совместимость);
`HostConfig.option_declarations: tuple[OptionDeclaration, ...] = ()`.

**Валидация при сборке** (`build_host_loop`): каждый `option_id` декларации
должен разрешаться в **существующую опцию окна**; `effect.fact`/`guard.fact`
должны быть согласованы с фактами исходов (иначе тихий промах); дубликаты
`option_id` запрещены. Несогласованность → `ValueError` на сборке (fail-fast),
а не молчаливая деградация.

`build_host_loop` собирает `GoalDirector`, если `goal.enabled` и
`actuation.enabled`; `HostLoop.step_once` вызывает `director.tick` после
аффективного тика. Декларации **накладываются** на опции окна (`replace`),
порядок окна сохраняется.

`selected_goal`, `goal_reason`, `goal_attempt`, `goal_achieved`,

## 10. Разделение общего и стенда A/B

| Общий механизм хоста | Стенд A/B (тест) |
|---|---|
| снимок фактов (`Environment.observe`) | состояния `a_serviced`, `b_serviced` |
| выбор неудовлетворённой цели (`select_goal`) | исходы «A обслужен», «B обслужен» |
| оценка опций по `effect` (`score_option`) | эффекты `service_a`, `service_b` |
| планирование и исполнение (`backward_chain`+executor) | вызов выбранного сервиса |
| проверка результата (`goal_reached`) | повторный `observe()` |

**Имена A/B не появляются** в общем скорере, `HostLoop`, `GoalDirector` или
config как специальные ветки — только в тестовом стенде (fixture). Ручное
объявление предпочтений и эффектов для MVP **нормально**: оно не доказывает
обучение, но честно проверяет выбор и исполнение на явной модели среды.

Стенд (тест-фикстура):

```python
class AbEnvironment:
    def observe(self) -> Mapping[str, float]:   # {"a_serviced": 0/1, "b_serviced": 0/1}
    def probe_fn(self, affordance) -> tuple[float, ...]:
        # service_a → a_serviced=1; service_b → b_serviced=1
        # флаги: forbid (оператор запретил) и lie (успех без изменения состояния)
```

## 11. Два разных вида успеха

| Вид | Определение | Источник |
|---|---|---|
| **Успех вызова** | инструмент завершился без технической ошибки | `ActuationStatus.SUCCESS` (эффектор) |
| **Успех цели** | наблюдаемое состояние удовлетворяет цели | `goal_reached(goal, re-observe)` |

Первое **не подменяет** второе. Если инструмент сообщил об успехе, а состояние
не изменилось — цель остаётся открытой; повторы ограничены `max_attempts`
(без бесконечного цикла).

## 12. Инварианты

1. **Цель не из колонки:** `selected_goal` формируется из исходов+фактов;
   `active_specialization` в оценку не входит (только трасса).
2. **Тотальность:** пустые исходы/неизвестный факт → деградация к дефолту, не
   падение; `selected_goal=None` при достигнутых исходах.
3. **Аддитивность скорера:** без `context.goal` pragmatic = 0 (совместимость
   S8 этапов 1–5).
4. **Два успеха не смешиваются:** закрытие цели только по наблюдению (§11).
5. **Одно действие в полёте:** нет параллельных запусков; повтор запрещён, пока
   цепочка не терминальна.
6. **Возврат в наблюдение:** результат актуации снова попадает в снимок фактов
   (замкнутый контур).
7. **Детерминизм:** при фиксированных входах и `latency_ticks` — одинаковая
   трасса; окно — мемоизированный снимок (ADR-0012 §9).
8. **Обратная совместимость:** `goal.enabled=False` → контур S8/S7 идентичен.
9. **Fail-safe:** отказ Gate/ошибка/тайм-аут → `FAILURE`, причина в трассе,
   цель открыта; повтор — в пределах `max_attempts`.
10. **S6/S8 без двойного вызова:** при активном S8 `explore()` подавлен, пока
    есть цель/действие в полёте (§8).

## 13. Критерии приёмки (на собранном хосте)

Главные тесты идут **через тот же управляющий цикл**, что и обычный запуск
(`HostLoop.run`/`step_once` с подключённым `GoalDirector`), не через ручной
вызов `select_option`/`tick_actuation` в тесте.

| Сценарий | Ожидаемый наблюдаемый результат |
|---|---|
| Только A требует обслуживания | выбрана цель A, вызван `service_a`, новое наблюдение подтверждает результат |
| Только B требует обслуживания | аналогично для B |
| Оба уже обслужены | нет ненужных вызовов (`selected_goal=None`) |
| Действие запрещено | нет вызова эффекторов; причина отказа доступна в трассе |
| Инструмент сообщил успех, состояние не изменилось | цель не закрыта; нет бесконечного повторения (≤ `max_attempts`) |
| Действие выполняется несколько тиков | один запуск, корректное ожидание (без повторного `start`) |
| Оператор изменил предпочтительный исход | следующий выбор отражает обновлённую цель по принятому правилу |

**Контроль против эффекта F (обязателен):** при одинаковом/сопоставимом общем
возбуждении ситуации «не обслужен A» и «не обслужен B» приводят к **разным**
инструментальным действиям (`service_a` vs `service_b`). Иначе показано только
изменение готовности действовать, а не содержательный выбор.

# ADR-0010: HITL-диагностика — протокол, пресеты и формальный sensitivity-harness

## Date
2026-10-04

## Status
Accepted

## Context

S1–S6 замкнули рефлекторную дугу и ввели автономию (S6 проход 1). Осталось
последнее звено валидации — **диалоговая диагностика человеком (HITL)**.
Она была отложена «на потом» (`VALIDATION.md` §6, BACKLOG `[HITL][docs]`), но
без неё ворота S3–S6 нечем закрывать по-человечески: pytest проверяет
инварианты, но не «тон следует аффекту» и не «уместность».

Проблемы, которые надо развести:

1. **Хаос ручек.** Настроек много (гомеостаз/policy/память/речь/пороги). Если
   наблюдатель крутит их в диалоге, прогоны несравнимы (VALIDATION §6).
2. **Числа vs категории.** Машина меряет числа, человек судит категориально
   («следует / частично / не следует»). Смешивать — значит либо навязывать
   человеку ложную точность, либо терять воспроизводимость.
3. **Адаптивность диагностики.** Жёсткий опросник не находит неожиданное;
   полностью свободный диалог не нормируется.
4. **Самоотчёт сброса** («я поплыл, нужен сброс») — критерий go S6, требует
   HITL-подтверждения исполнения сброса (fail-safe deny).

Ограничения:
- ADR-0005 §9: необратимое — только через HITL, fail-safe deny.
- ADR-0007: LLM — актюатор, не судья; диагностика не делегируется LLM.
- Манифест §3.И: HITL не оценивает «сознание» — только наблюдаемое поведение;
  риск антропоморфной самообманки (тёплый тон ≠ надёжность).
- CONSTITUTION §2.2: пороги — в `src/config/`.
- Не вводить новых зависимостей без решения.

## Decision

### 1. HITL-диагностика — отдельный этап S7, не проход 2 S6

Диалоговая диагностика выделяется в **самостоятельный этап S7** со своим
SPEC/PLAN/протоколом. S6 проход 2 (длинный горизонт C10, ночной цикл, MCP)
остаётся про автономию; S7 использует уже готовые механики (selfcontrol,
fingerprint, gate) как инструменты. Причина: диагностика — это мета-слой
валидации, а не часть автономии; смешение раздувает S6.

### 2. Две независимые части: формальный тест и HITL-диалог

| | Формальный технический тест | HITL-диалог |
|---|---|---|
| Предмет | числа, пороги, детерминизм | категории наблюдаемого поведения |
| Ручки | **крутятся здесь** (матрица возмущений) | **заморожены пресетом** |
| Проверка | инварианты направления/границ | «следует / частично / не следует» |
| Повторяемость | полная (seed + injection) | путь зависит от ответов (логируется) |

Ручки **не крутятся в диалоге** — иначе прогоны несравнимы. Чувствительность
к ручкам — прерогатива формального harness.

### 3. Sensitivity-harness: хардкод матрицы, проверка инвариантов направления

Формальный harness (`src/tests/test_sensitivity.py` + CLI `--sensitivity`)
хардкодит **какие ручки** и **диапазоны** возмущать (например
`f_threshold ∈ {0.5, 1.0, 2.0}`), но проверяет **инварианты**, а не точные
значения: «рост `f_threshold` не увеличивает частоту реплик», «talk-rate ∈
[0,1]», «тот же seed → тот же fingerprint». Точные значения — калибровка
(BACKLOG `[S4][policy] Калибровка порогов`), их хардкодить нельзя.

Машина утверждает **направление** («ниже порог → больше речи»), но не
**желательность** («это не болтливо») — желательность судит человек.

### 4. HITL-вердикт = категория + комментарий + числовой snapshot

Человек даёт **категориальную** оценку (порядковая шкала `соответствует /
частично / не соответствует` — без ложной точности) и свободный комментарий.
Числовой `snapshot` (F/val/stress/γ/задача/партнёр/метакогниция/сброс)
прикладывается к вердикту, но **не оценивается** человеком — для последующего
анализа.

**Мост:** категориальные находки диалога офлайн коррелируются с числами →
рождают **новый машинный тест**. Диалог обнаруживает явление, формальный тест
его замораживает. Две части не разъезжаются.

### 5. Мобильное ветвление по ответам, не по ручкам

Диагностическая сессия — последовательность **проб** (probes). Каждая проба:
`{id, стадия, preset, скрипт событий, вопрос, шкала, правило_ветвления}`.
По категориальному ответу выбирается следующая проба (углубление или переход к
следующему блоку). Ручки не трогаются: пресет фиксирует неизменяемое, ветвление
даёт адаптивность.

### 6. Пресеты — гибрид: Python-база + TOML-override

Пресет — именованный снимок конфигурации, привязанный к сценарию. Реализация —
**гибрид** (вариант 3):
- **база** — `src/config/presets.py`: типобезопасные фабрики `HostConfig`
  (`baseline`, `stress`, `dialogue`, `autonomy`, `long-horizon`, `cooperative`);
- **override** — `configs/*.toml`, загружаемые поверх базы (stdlib `tomllib`,
  **без новой зависимости**), с валидацией через `HostConfig`.

База гарантирует безопасный детерминизм (seed, synthetic clock, fake LLM/embedder
для воспроизводимости); override позволяет наблюдателю адаптировать явно
разрешённое без пересборки.

### 7. Sensitivity-harness — и pytest (CI-гейт), и CLI (отладка)

Формальный harness доступен **и** как pytest (`test_sensitivity.py` — гейт в
CI), **и** как CLI `--sensitivity` (ручной просмотр матрицы возмущений и
отпечатков). Одна Core-логика (`src/host/fingerprint.py`, вынос
`behavioral_fingerprint` из тестов), два входа.

### 8. Самоотчёт сброса — диалоговый интент с HITL-подтверждением

Когда `SelfMonitor` возвращает `ResetPlan(triggered=True)` (SOFT/FREEZE), хост
формулирует **самоотчёт** («я поплыл, нужен сброс: причина X») отдельным
речевым интентом (не путать с инициативой). Исполнение сброса требует
HITL-подтверждения через capability gate (fail-safe deny при таймауте,
ADR-0005 §9). `HARD` — аварийная остановка, не сброс.

### 9. Формальный тест не заменяет SDD

Пресеты, harness и диагностический журнал пишутся по SPEC/PLAN до кода
(CONSTITUTION §5.1). Протокол (`stages/S7_HITL_PROTOCOL.md`) — операторский
документ: чек-лист, дерево проб, границы.

## Consequences

### Положительные
- Прогоны **воспроизводимы** (пресеты) и **нормируемы** (категории + snapshot).
- Числа и категории разведены: нет ложной точности и нет потери форензики.
- Адаптивность через ветвление, а не через хаос ручек.
- Мост «диалог → машинный тест» замыкает обратную связь валидации.
- Нет новой зависимости (TOML — stdlib).

### Отрицательные
- Ещё один этап и документ; нужна дисциплина заполнения протокола.
- Категориальная шкала грубее числовой (осознанный компромисс).
- Мост требует ручной офлайн-корреляции (позже автоматизируется).

### Tradeoffs
- **Python-пресеты vs TOML:** чистый Python типобезопасен, но не правится на
  лету; чистый TOML гибок, но требует валидации. Гибрид берёт оба плюса.
- **Структура vs свобода:** фиксированные пробы нормируются, но не находят
  неожиданное; свободный комментарий сохраняет находки, ветвление — глубину.

## Confidence
Medium-High. Разделение «машина меряет числа / человек судит категории» и
«ручки — в формальном тесте» следует из VALIDATION §6 и практики HITL.
Конкретные пресеты, пробы и пороги ветвления будут уточняться при реализации.
